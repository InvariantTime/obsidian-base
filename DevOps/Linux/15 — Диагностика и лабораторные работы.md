# Диагностика и лабораторные работы

## Универсальный алгоритм

1. Точно описать симптом: что ожидалось, что произошло, когда началось.
2. Определить слой: команда, права, процесс, служба, сеть, диск, память.
3. Собрать состояние до изменения.
4. Проверить одну гипотезу одним минимальным действием.
5. Сравнить результат и записать вывод.
6. Откатить временную диагностику.

Не начинайте с перезагрузки или переустановки: они стирают часть свидетельств и не объясняют причину.

## Карта первичной проверки

| Симптом | Проверки |
| --- | --- |
| command not found | `type -a`, `command -v`, `PATH`, установлен ли пакет |
| Permission denied | `id`, `namei -l <путь>`, `ls -ld`, точка монтирования, ACL |
| сервис не запускается | `systemctl status`, `journalctl -u`, проверка конфигурации |
| порт недоступен | `ss -lntup`, адрес bind, firewall, route, DNS |
| нет места | `df -hT`, `df -i`, `du -x`, `lsof +L1` |
| машина тормозит | `uptime`, `top`, `free`, `ps`, журнал kernel |

`Permission denied` не всегда исправляется `chmod 777`: может отсутствовать `x` у родительского каталога, файловая система быть read-only/noexec, мешать ACL или политика SELinux/AppArmor. Сначала ищите точную проверку, которая отказала.

## Лаборатория 1: дерево файлов

1. Создайте `~/linux-lab/{input,output,bin}`.
2. Создайте файлы с обычным именем, пробелом и именем `-example`.
3. Скопируйте их, используя кавычки и `--`.
4. Создайте символическую и жёсткую ссылки, сравните `stat`.
5. Удалите исходное имя и объясните состояние обеих ссылок.

## Лаборатория 2: права

1. Создайте каталог `shared` и файлы с umask `022` и `077`.
2. Предскажите права до `ls -l`.
3. Измените группу файла на группу, членом которой вы являетесь.
4. Проверьте доступ к каталогам при разных сочетаниях `r`, `w`, `x`.
5. Верните безопасные права после опыта.

## Лаборатория 3: процессы

```bash
sleep 300 &
job_pid=$!
ps -o pid,ppid,stat,cmd -p "$job_pid"
kill -STOP "$job_pid"
ps -o pid,stat,cmd -p "$job_pid"
kill -CONT "$job_pid"
kill -TERM "$job_pid"
wait "$job_pid"
```

Объясните различие shell job ID, PID, сигнала STOP и завершения TERM.

## Лаборатория 4: служба пользователя

Создайте user service `Type=oneshot`, который через `date --iso-8601=seconds` дописывает дату в файл лаборатории. Запустите через `systemctl --user start`, найдите запись в `journalctl --user`, затем добавьте timer. Не используйте root.

## Итоговый проект

Напишите скрипт диагностики, который без `sudo` собирает в каталог: дату, `/etc/os-release`, `uname -r`, `uptime`, `free -h`, `df -hT`, `ip addr`, `ip route`, список failed user units. Скрипт должен:

- создавать новый каталог, не перезаписывая старый;
- цитировать переменные;
- продолжать работу, если необязательная команда отсутствует;
- записывать ошибки отдельно;
- упаковывать результат в `.tar.gz` и печатать SHA-256.

Вернуться: [[Linux MOC]].

## Как задавать хороший диагностический вопрос

Вместо «Linux не работает» соберите:

- точную команду без секретов;
- полный текст ошибки;
- ожидаемый результат;
- дистрибутив и версию;
- что изменилось перед проблемой;
- воспроизводится ли снова;
- какие безопасные проверки уже сделаны.

Не публикуйте токены, private keys, cookies, `/proc/PID/environ`, полные конфиги с паролями и приватные адреса без необходимости.

## Не путайте симптом и причину

Пример: веб-сайт не открывается. Симптом — timeout браузера. Возможные причины: DNS, route, firewall, процесс не запущен, bind на loopback, TLS, proxy, приложение зависло. «Перезапуск Nginx помог» не доказывает, что Nginx был первопричиной; нужны журнал и состояние до перезапуска.

## Метод сравнений

Полезные пары:

- работает локально / не работает удалённо;
- работает от root / не работает от пользователя;
- работает по IP / не работает по имени;
- работает вручную / не работает в systemd/cron;
- работало до обновления / сломалось после;
- один файл работает / другой с теми же ожидаемыми правами нет.

Различие сужает слой. Например, IP работает, имя нет — сначала DNS/NSS, а не переустановка приложения.

## Лаборатория 5: диагностика Permission denied

Создайте дерево с каталогом без `x`, файлом без `r` и скриптом без execute bit. Для каждой ошибки соберите `id`, `namei -l`, `stat`, `getfacl`, `findmnt -T`. Исправьте минимально необходимый бит и объясните, почему именно его.

## Лаборатория 6: локальный HTTP

Если установлен Python:

```bash
mkdir -p ~/linux-lab/http
printf 'hello\n' > ~/linux-lab/http/index.html
python3 -m http.server 8000 --directory ~/linux-lab/http
```

Во втором терминале проверьте `ss -lntp`, `curl -v http://127.0.0.1:8000/`, найдите PID и завершите через Ctrl+C. Определите адрес bind и объясните, доступен ли сервер с другой машины.

## Лаборатория 7: заполнение inode в миниатюре

Не заполняйте настоящую файловую систему. Вместо этого изучите текущие значения `df -h` и `df -i`, создайте в отдельном каталоге 100 маленьких файлов, снова сравните. Объясните, почему содержимое почти не занимает блоки, но каждый файл использует метаданные.

## Лаборатория 8: восстановление

1. Создайте дерево с текстом, ссылкой и правами.
2. Упакуйте через `tar` с сохранением метаданных.
3. Посчитайте SHA-256.
4. Восстановите в новый каталог.
5. Сравните содержимое, ссылки, владельца и права.

Цель backup — восстановление, поэтому тест restore важнее факта создания архива.

## Итоговая самопроверка

Вы готовы переходить к более продвинутому Linux, если можете без подсказки объяснить:

1. чем terminal отличается от shell;
2. как абсолютный путь отличается от относительного;
3. почему удалённый открытый файл занимает место;
4. как выбирается набор owner/group/other;
5. почему `x` каталога не равен выполнению каталога;
6. чем программа отличается от процесса;
7. почему TERM предпочтительнее KILL;
8. чем active отличается от enabled;
9. почему `apt update` не обновляет установленные программы;
10. как разложить сетевую ошибку на DNS, route, port, TLS и приложение;
11. почему высокая занятая RAM не всегда проблема;
12. почему cron-задача требует явного окружения.
