# Сервисы и журналы

На большинстве современных дистрибутивов systemd — менеджер запуска и сервисов. Он управляет юнитами: `.service`, `.socket`, `.timer`, `.mount` и другими. Не каждая Linux-система использует systemd: тогда команды этой заметки не подойдут.

```bash
systemctl status ssh
sudo systemctl start ssh
sudo systemctl stop ssh
sudo systemctl restart ssh
sudo systemctl reload ssh
sudo systemctl enable ssh
sudo systemctl disable ssh
```

Имя службы зависит от дистрибутива: SSH может называться `ssh` или `sshd`. Ищите так: `systemctl list-unit-files | grep -i ssh`.

## Журнал

```bash
journalctl -b
journalctl -u ssh --since today
journalctl -f
journalctl -p warning..alert -b
```

`journalctl -f` похож на `tail -f`, но читает журнал systemd. На части систем логи также лежат в `/var/log`; точный путь определяют дистрибутив и настройки службы.

Перед изменением конфигурации: проверьте синтаксис инструментом сервиса (например, `nginx -t`), сохраните копию, примените безопасный `reload` только при его поддержке и затем посмотрите статус/журнал. Официальные страницы: [systemctl](https://www.freedesktop.org/software/systemd/man/systemctl.html), [systemd.service](https://www.freedesktop.org/software/systemd/man/systemd.service.html).

## start не равен enable

- `start` запускает юнит сейчас, но не обязательно при следующей загрузке;
- `enable` создаёт связи для запуска при достижении target, но обычно не запускает сейчас;
- `enable --now` делает оба действия;
- `mask` запрещает запуск, связывая юнит с `/dev/null`;
- `disable` удаляет enable-связи, но не останавливает уже работающий сервис.

```bash
systemctl is-active ssh
systemctl is-enabled ssh
systemctl show ssh -p ActiveState -p SubState -p UnitFileState
```

## Где находится конфигурация юнита

```bash
systemctl cat ssh
systemctl show ssh -p FragmentPath -p DropInPaths
systemctl edit ssh
```

Не редактируйте файл пакета в `/usr/lib/systemd/system` или `/lib/systemd/system`: обновление его заменит. `systemctl edit` создаёт drop-in в `/etc/systemd/system/<unit>.d/`. После ручного изменения unit-файлов нужен `systemctl daemon-reload`; это перечитывает конфигурацию systemd, но не перезапускает сервис.

## Зависимости и порядок

`After=` задаёт порядок запуска, но само по себе не притягивает другой юнит. `Requires=`/`Wants=` задают зависимости, но не всегда нужный порядок. Наличие `After=network.target` не означает, что Интернет или DNS уже доступны. Надёжная служба должна переносить временную недоступность сети и повторять подключение.

```bash
systemctl list-dependencies ssh
systemctl show ssh -p Wants -p Requires -p After
```

## Состояния сервиса

Для `Type=simple` systemd считает сервис запущенным после старта процесса; для `Type=notify` приложение явно сообщает готовность; `Type=oneshot` предназначен для конечного действия. `active` не всегда означает, что бизнес-функция здорова — дополнительно проверяйте порт, endpoint или ожидаемый результат.

## journalctl как запрос

```bash
journalctl -u nginx.service -b --no-pager
journalctl _PID=<PID>
journalctl _SYSTEMD_UNIT=nginx.service -o json-pretty
journalctl --disk-usage
```

Journal хранит структурированные поля, поэтому фильтрация по unit/PID надёжнее `grep` по всей строке. Сохранение между перезагрузками зависит от конфигурации journald и наличия persistent storage.

## Пользовательские сервисы

```bash
systemctl --user status
systemctl --user list-units --type=service
journalctl --user -b
```

User units не требуют root и подходят для личных фоновых приложений. Они имеют отдельный manager и каталог `~/.config/systemd/user/`; не смешивайте их с системными units.

## Что такое служба

Служба — программа, которая выполняет фоновую функцию: веб-сервер, база данных, SSH, сборщик логов. Просто запустить `app &` недостаточно: кто-то должен запустить её после reboot, корректно остановить, собрать вывод и решить, что делать после сбоя. Service manager решает эту задачу.

Systemd хранит желаемую конфигурацию в unit-файле и текущее состояние в памяти. Команда `systemctl` обращается к manager, а не напрямую «убивает процесс».

## Разбираем status

```bash
systemctl status ssh --no-pager
```

В выводе ищите:

- `Loaded` — откуда загружен unit и включён ли автозапуск;
- `Active` — активен, завершён с ошибкой, активируется и т. п.;
- `Main PID` — основной процесс, если применимо;
- последние строки журнала;
- код выхода и причина завершения.

Статус `active (exited)` может быть нормальным для `Type=oneshot`: действие завершилось, а unit считается активным. `active (running)` ещё не гарантирует, что приложение отвечает корректно.

## Минимальный пользовательский service

Создайте `~/.config/systemd/user/hello.service`:

```ini
[Unit]
Description=Beginner hello service

[Service]
Type=oneshot
ExecStart=/usr/bin/printf Hello-from-systemd\n
```

Примените и проверьте:

```bash
systemctl --user daemon-reload
systemctl --user start hello.service
systemctl --user status hello.service --no-pager
journalctl --user -u hello.service --no-pager
```

В `ExecStart=` не работает полный синтаксис интерактивного Bash: `|`, `>`, `&&` не становятся shell-операторами автоматически. Если логика сложная, вынесите её в проверенный исполняемый скрипт или явно используйте shell с осторожным quoting.

## restart, reload и reload-or-restart

- restart останавливает и запускает процесс заново; соединения могут оборваться;
- reload просит работающую программу перечитать конфигурацию;
- reload существует только если unit/программа это поддерживают;
- reload-or-restart выбирает reload, иначе restart.

Перед reload проверяйте конфигурацию штатной командой приложения. Ошибка в новом конфиге может оставить службу на старой конфигурации или привести к отказу — поведение зависит от программы.

## Чтение журнала по времени

```bash
journalctl -u ssh.service --since '10 minutes ago'
journalctl -u ssh.service --since '2026-07-25 12:00' --until '2026-07-25 12:30'
journalctl -b -1 -p warning
```

Сначала ограничьте unit, boot и временной интервал, затем ищите текст. Ошибка ближе к началу цепочки часто важнее последующих сообщений о неудачных повторах.

## Частые ошибки новичка

- После изменения unit забыть `daemon-reload`.
- Сделать `enable`, но ожидать немедленного запуска.
- Запустить `restart` до проверки конфигурации.
- Читать только `status`, хотя нужная причина выше в `journalctl`.
- Редактировать файл пакета вместо drop-in.
- Считать, что имя процесса и имя unit обязаны совпадать.

## Упражнения

1. Найдите пять активных services через `systemctl --type=service --state=running`.
2. Для безопасной службы только прочитайте `cat`, `show` и зависимости.
3. Создайте user oneshot из примера и найдите его сообщение в journal.
4. Объясните разницу между `active`, `enabled` и `failed`.
