# Пользователи и права

У процесса есть эффективные UID и группы. Ядро проверяет их при доступе к файлам и при многих системных операциях.

## Владелец, группа и rwx

```bash
ls -l report.txt
# -rw-r----- 1 alice developers 1200 Jul 25 10:00 report.txt
chmod u+x script.sh
chmod 640 report.txt       # u=rw, g=r, o=---
chown alice:developers report.txt # обычно через sudo
id
```

После типа объекта идут права владельца, группы и остальных. `r` — чтение, `w` — запись, `x` — выполнение. Для **каталога** `r` показывает имена, `w` позволяет создавать/удалять записи (при нужном `x`), а `x` разрешает проход по каталогу и доступ по имени.

Числа: `r=4`, `w=2`, `x=1`; поэтому `640` = `rw- r-- ---`.

## Пользователи, группы и sudo

```bash
getent passwd alice
getent group sudo
sudo -v               # проверить/обновить кэш авторизации
sudo -l               # разрешённые команды
```

Не редактируйте `/etc/sudoers` обычным редактором. Используйте `visudo`: он проверяет синтаксис. Для ежедневной работы используйте обычную учётную запись и выдавайте минимальные необходимые права.

## ACL и специальные биты

ACL дополняют три стандартных набора прав:

```bash
getfacl shared
setfacl -m u:bob:rw shared/file.txt
```

После ACL в `ls -l` часто появляется `+`. Sticky bit на `/tmp` — пример специальных правил: пользователи обычно могут создавать там файлы, но не удалять чужие. `setuid` и `setgid` требуют отдельного изучения и не должны включаться «для исправления доступа».

## Какие идентификаторы есть у процесса

Процесс имеет real, effective и saved UID/GID, а также список дополнительных групп. Для большинства проверок файлов важны effective IDs. Обычный пользователь имеет UID вроде 1000; root традиционно UID 0. Имя — удобное отображение, ядро хранит числовой идентификатор.

```bash
id
id alice
getent passwd alice
getent group developers
ps -o pid,user,group,euser,egroup,cmd -p $$
```

`/etc/passwd` содержит не пароли, а имя, UID/GID, домашний каталог и shell. Хеши локальных паролей обычно находятся в защищённом `/etc/shadow`. `getent` предпочтительнее прямого чтения, потому что учётные записи могут приходить не только из файлов, но и из LDAP/SSSD и других настроенных источников.

## Как выбирается набор rwx

Упрощённо ядро сравнивает владельца файла с effective UID процесса. Если совпало, применяются **только** биты владельца. Иначе, если группа файла входит в группы процесса, применяются биты группы. Иначе — биты others. Наборы не складываются: пользователь-владелец с `---` не получит `r` из группы файла.

После обычных битов результат могут ограничить ACL, атрибуты файловой системы, read-only/noexec mount, capabilities, SELinux/AppArmor и другие механизмы.

## Umask

Umask убирает права при создании объекта; она не изменяет уже существующие файлы.

```bash
umask
umask 027
touch new-file           # запрос 666 минус запрещённые биты -> обычно 640
mkdir new-directory      # запрос 777 -> обычно 750
```

Формально режим без default ACL получается как `requested_mode & ~umask`. Обычные файлы не получают `x` автоматически: программа при создании обычно запрашивает `0666`, каталоги — `0777`.

## Совместный каталог через группу

```bash
sudo install -d -o root -g developers -m 2775 /srv/project
```

Первая `2` включает setgid на каталоге: новые объекты обычно наследуют его группу. Чтобы совместная запись работала предсказуемо, нужны подходящая umask/default ACL и членство пользователей в группе. После добавления в группу существующая сессия может не увидеть её до нового входа; проверьте `id`.

## Изменение пользователя

```bash
sudo -u postgres id
sudo -iu alice
su - alice
```

`sudo -u` запускает отдельную команду от другого пользователя. Login-режим (`-i` у sudo или `-` у su) создаёт окружение, похожее на новый вход. Не путайте права процесса и владельца файлов: запуск редактора через `sudo` может оставить root-файлы в домашнем каталоге.

## Capabilities

Linux разделяет часть полномочий root на capabilities, например привязку к привилегированному порту или изменение владельца. Они являются свойствами потоков и могут назначаться исполняемым файлам.

```bash
getcap -r /usr/bin 2>/dev/null
getpcaps $$
```

Capability — не «безопасный sudo» автоматически: отдельное полномочие может дать широкий путь к повышению прав. Назначайте их только после анализа конкретной программы. Подробнее: [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html).

## Диагностика Permission denied

1. `id` — кто выполняет операцию и какие группы активны.
2. `namei -l <путь>` — права каждого каталога пути.
3. `getfacl <путь>` — ACL и mask.
4. `findmnt -T <путь> -o TARGET,SOURCE,FSTYPE,OPTIONS` — `ro`, `noexec`, `nosuid`.
5. Журналы SELinux/AppArmor, если базовые права разрешают операцию.

`chmod 777` отключает полезные ограничения и часто не исправляет реальную причину.
