# Память и ресурсы

## Память

Linux старается использовать свободную RAM для кэша файлов: полностью «пустая» память не является целью. Поэтому смотрите на `available`, а не только на `free`.

```bash
free -h
cat /proc/meminfo | less
ps -eo pid,user,%mem,rss,vsz,cmd --sort=-rss | head
```

- RSS — страницы процесса, находящиеся в RAM; часть может быть общей с другими процессами.
- VSZ — виртуальное адресное пространство, не фактически занятая RAM.
- swap — место на диске для вытесненных страниц; его использование само по себе не доказывает проблему.

При исчерпании памяти ядро может вызвать OOM killer и завершить процесс. Ищите записи через `journalctl -k -g 'Out of memory|Killed process'` (поддержка `-g` зависит от версии) или `journalctl -k | grep -Ei 'out of memory|killed process'`.

## CPU и load average

```bash
uptime
top
ps -eo pid,pcpu,stat,comm --sort=-pcpu | head
nproc
```

Load average — среднее число задач, которые выполняются/готовы выполняться и задач в непрерываемом ожидании. Его нельзя напрямую считать «процентом CPU». Значение 4 имеет разный смысл на машине с 2 и 32 логическими CPU; высокий load может быть вызван I/O.

## Диск и I/O

```bash
df -hT
df -ih                 # использование inode
du -xhd1 /var 2>/dev/null | sort -h
lsblk -f
```

Если `df` заполнен, а `du` не находит данные, проверьте удалённые, но открытые файлы: `sudo lsof +L1`. Место освободится после закрытия файлового дескриптора; не обнуляйте `/proc/<PID>/fd/...` без понимания приложения.

## Файловые дескрипторы и лимиты

```bash
ulimit -a
ls -l /proc/$$/fd
lsof -p <PID>
cat /proc/<PID>/limits
```

Открытые файлы, сокеты и каналы представлены дескрипторами. Ошибка `Too many open files` может означать утечку в приложении или слишком низкий лимит; простое повышение лимита иногда лишь откладывает отказ. Сначала посмотрите количество и тип открытых объектов.

## Инструменты по слоям

| Вопрос | Первый инструмент |
| --- | --- |
| закончилась RAM? | `free -h`, `journalctl -k` |
| кто грузит CPU? | `top`, `ps --sort=-pcpu` |
| где занято место? | `df`, затем `du` |
| закончились inode? | `df -i` |
| кто слушает порт? | `ss -lntup` |
| какие файлы открыл процесс? | `lsof -p PID`, `/proc/PID/fd` |

Снимайте показатели несколько раз: один снимок не показывает динамику.

## Почему Linux заполняет память кэшем

Чтение с диска медленнее RAM, поэтому ядро сохраняет недавно использованные страницы файлов в page cache. Когда приложению нужна память, кэш можно освободить. Поле `available` оценивает, сколько памяти можно предоставить без активного swapping, включая часть освобождаемого кэша.

Не очищайте кэш вручную ради красивого `free`: это обычно ухудшает производительность и не устраняет утечку приложения.

## Виртуальная память простыми словами

Каждый процесс видит собственное виртуальное адресное пространство. Адреса отображаются на физические страницы RAM, файлы или ещё не выделенные области. Поэтому VSZ может быть огромным без соответствующего расхода RAM.

```bash
pmap -x <PID> | tail -n 20
cat /proc/<PID>/smaps_rollup
```

RSS включает resident pages, но shared pages могут учитываться в нескольких процессах. Для точной атрибуции существуют PSS и специализированные инструменты.

## Swap не всегда проблема

Ядро может вытеснить давно неиспользуемые страницы и оставить больше RAM для полезного кэша. Проблема — постоянное интенсивное перемещение между RAM и swap (thrashing), сопровождаемое задержками. Наблюдайте динамику через `vmstat 1` (`si`/`so`), задержки и pressure, а не одно число.

## CPU time и wall time

- wall time — сколько реального времени прошло;
- user CPU — время выполнения пользовательского кода;
- system CPU — время в kernel;
- I/O wait — CPU простаивает при ожидаемом I/O в агрегированной статистике.

```bash
time command
pidstat -p <PID> 1       # пакет sysstat, если установлен
```

Многопоточная программа может накопить CPU time быстрее wall time, потому что несколько потоков работают одновременно.

## Load average на примере

На 4-CPU системе устойчивый load около 4 может означать полностью занятую вычислительную очередь без большого ожидания. Load 8 означает в среднем больше готовых/ожидающих задач, чем одновременно исполняется. Но задачи в состоянии D также входят в Linux load, поэтому всегда сопоставляйте с CPU usage и I/O.

## Pressure Stall Information

Если поддерживается ядром:

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

PSI показывает долю времени, когда задачи задерживались из-за дефицита ресурса. Это полезнее простого «память занята на 90%», но требует понимания интервалов `avg10/60/300` и `total`.

## Пошаговая диагностика торможения

1. `uptime` — load и время работы.
2. `top` — CPU, memory, процессы и состояния.
3. `free -h` — available и swap.
4. `vmstat 1` — очередь, swap, I/O, CPU во времени.
5. `df -hT` и `df -i` — место.
6. Журнал kernel — OOM, I/O errors, throttling.
7. Специализированный инструмент по найденному слою.

## Упражнение

Запустите `yes > /dev/null &`, запомните PID и наблюдайте его в `top`/`ps`. Уменьшите приоритет через `renice 10 -p PID`, затем завершите TERM. Это создаёт CPU-нагрузку; не запускайте много копий на слабой машине.
